## 1. 项目概览

| 维度 | 详情 |
|------|------|
| **项目名称** | AI教学平台 (AI Teaching Platform) |
| **技术栈** | FastAPI + SQLAlchemy 2.0 (异步) + PostgreSQL/SQLite + MinIO + Redis |
| **前端** | React 18 + TypeScript + Vite + Ant Design 5 + Zustand + ECharts |
| **部署** | Docker Compose (开发/生产双配置) + Nginx 反向代理 |
| **认证** | JWT (Access + Refresh Token) + Token版本失效 + bcrypt密码哈希 |
| **核心模块** | 用户认证、课程管理、学生管理、成长档案(Portfolio)、教案中心、资源中心、报告分析、通知系统、AI助手(占位) |

### 架构评估

- **后端分层**: API路由层 -> 服务层 -> 数据模型层，分层清晰
- **前端分层**: 页面组件 -> 服务层(API调用) -> 状态管理(Store)，结构合理
- **异常处理**: 后端有完善的 BusinessException 体系和全局异常处理器
- **安全措施**: JWT + bcrypt + Token版本控制 + 软删除 + 用户数据隔离 + 速率限制
- **存储**: MinIO + 本地文件系统自动降级，设计合理

### 数据流转路径

```
前端页面 -> services/*.ts (API调用) -> axios拦截器(附加Token/刷新) 
  -> /api/v1/* 路由 -> Service层(业务逻辑) -> Model层(SQLAlchemy ORM) -> 数据库
```

**整体评价**: 项目的架构基础良好，核心CRUD功能模块（课程、学生、教案、资源、成长档案）的数据流转通畅。但存在若干**阻断交付的关键问题**需要优先解决。

### C-03 注册页面前后端密码强度校验不一致

| 属性 | 内容 |
|------|------|
| **严重程度** | **Critical** |
| **影响范围** | 用户注册流程 |
| **触发条件** | 用户输入仅含小写字母+数字的8位密码 |

**具体表现**:

前端 [Register/index.tsx](file:///d:/Projects/ai-teaching-platform/frontend/src/pages/Register/index.tsx#L61-L72) 校验规则:
```javascript
if (value.length < 8) return reject('密码长度至少为8位')
if (!/(?=.*[A-Za-z])(?=.*\d)/.test(value)) return reject('密码必须同时包含字母和数字')
// 注意: 此正则只检查"字母(大小写均可)"+"数字"，不强制要求大写
```

后端 [auth.py](file:///d:/Projects/ai-teaching-platform/backend/app/schemas/auth.py#L23-L33) 校验规则:
```python
def validate_password_strength(value: str) -> str:
    if len(value) < 8: raise ValueError("密码长度至少8位")
    if not any(ch.isupper() for ch in value): raise ValueError("密码必须至少包含一个大写字母")
    if not any(ch.islower() for ch in value): raise ValueError("密码必须至少包含一个小写字母")
    if not any(ch.isdigit() for ch in value): raise ValueError("密码必须至少包含一个数字")
```

**影响**: 密码 `abcdef12` 可通过前端校验但被后端拒绝。用户在前端看到"注册成功"提示后实际请求返回422验证错误，体验极差且可能丢失用户。

**建议解决方案**:
将前端密码校验规则与后端对齐:
```javascript
// 修改 Register/index.tsx 第68行
if (!/(?=.*[A-Z])(?=.*[a-z])(?=.*\d)/.test(value)) {
  return Promise.reject(new Error('密码必须包含大写字母、小写字母和数字'))
}
```
同时更新占位提示文字。

4. 在学生详情页增加"已选课程"标签

## 3. High 高优先级问题

### H-01 API路由重复注册导致OpenAPI Schema冗余

| 属性 | 内容 |
|------|------|
| **严重程度** | **High** |
| **影响范围** | API文档可读性、自动生成客户端代码 |

**具体表现**:
多个路由模块使用了双路由注册模式，例如 [students.py](file:///d:/Projects/ai-teaching-platform/backend/app/api/v1/students.py#L40-L41):
```python
@router.post("/", ..., include_in_schema=False)
@router.post("", ...)  # 无尾部斜杠版本
```
虽然 `include_in_schema=False` 隐藏了重复路由，但:
1. 增加了代码维护复杂度
2. 部分路由（如 `get_lesson_plans`）两个装饰器中 `include_in_schema=False` 放在第一个路由上，但第一个路由带 `/` 而第二个不带。如果前端请求 `/lesson-plans/`（带斜杠），实际匹配的是第一个被隐藏的路由

**建议解决方案**:
统一使用无尾部斜杠的路由（FastAPI默认行为），移除所有双路由注册模式。FastAPI已自动处理斜杠重定向。

### H-02 学生学习进度算法过于简单

| 属性 | 内容 |
|------|------|
| **严重程度** | **High** |

### H-04 前端登录错误提示过于笼统

| 属性 | 内容 |
|------|------|
| **严重程度** | **High** |
| **影响范围** | 用户体验 |

**具体表现**:
[Login/index.tsx](file:///d:/Projects/ai-teaching-platform/frontend/src/pages/Login/index.tsx#L34-L35):
```javascript
} catch {
  message.error('登录失败，请检查用户名和密码')
}
```
- 无论后端返回什么错误（账户锁定、已禁用、密码错误等），都显示相同的笼统提示
- 后端返回的 `BusinessError` 包含精确的错误码（如 `ACCOUNT_LOCKED`），但前端未利用

**建议解决方案**:
在catch块中解析 `BusinessError`，根据 `errorCode` 显示对应中文提示:
```javascript
catch (error) {
  if (error instanceof BusinessError) {
    const errorMessages = {
      'ACCOUNT_LOCKED': '账户已被锁定，请稍后再试',
      'ACCOUNT_DISABLED': '账户已被禁用，请联系管理员',
      'INVALID_CREDENTIALS': '用户名或密码错误',
    }
    message.error(errorMessages[error.code] || '登录失败')
  }
}
```

### H-05 认证Token存储在localStorage

| 属性 | 内容 |
|------|------|
| **严重程度** | **High** |
| **影响范围** | 安全性 |

**具体表现**:
[auth.ts store](file:///d:/Projects/ai-teaching-platform/frontend/src/stores/auth.ts#L20-L22):
```javascript
localStorage.setItem('token', token)
localStorage.setItem('refreshToken', refreshToken)
```
- localStorage 对同源所有JS代码可见，XSS攻击可直接窃取Token
- 虽然后端设置了安全响应头（CSP、X-Frame-Options等），但深度防御原则下不应完全依赖

**建议解决方案**:
1. 将Refresh Token改为httpOnly Cookie存储（需后端配合设置Set-Cookie响应头）
2. Access Token可保留在内存（Zustand store）中，页面刷新后通过Refresh Token静默获取新Access Token
3. 或使用BFF（Backend for Frontend）模式

### M-05 前端Response拦截器统一解包有边界风险

| 属性 | 内容 |
|------|------|
| **严重程度** | **Medium** |
| **影响范围** | API数据处理 |
| **相关文件** | [request.ts](file:///d:/Projects/ai-teaching-platform/frontend/src/services/request.ts#L93-L120) |

**表现**: `request.ts` 的响应拦截器自动将 `response.data.data` 解包返回。判断逻辑为:
```javascript
if (responseData && responseData.data !== undefined) {
  // 检查是否有列表元数据字段
  if (hasListMeta) return responseData  // 保留完整结构
  return responseData.data  // 自动解包
}
```
风险：
- 若后端返回 `{data: null}` 的合法响应，会被解包返回 `null`
- 判断列表元数据的逻辑依赖字段名匹配（`total`/`page`/`page_size`等），如果后端新增其他带此类字段的包装响应可能被误判

**建议**: 在后端统一响应格式或在拦截器中基于更明确的标志位判断，或完全取消自动解包。
